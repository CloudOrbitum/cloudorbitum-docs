# AGENTS.md — Orbitum docs

Guidance for AI agents working in this repository. It is modelled on cloudflare-docs' `AGENTS.md`: same framework, same content model, Orbitum's design system and content style.

Read also:
- [AGENT.md](AGENT.md) — the Nimbus framework guide that came with the starter (sidebar, API reference, upgrades, audit). Upstream-owned; don't rewrite it.
- `node_modules/@cloudflare/nimbus-docs/dist/docs-for-agents.md` — the release-matched framework guide.
- `../orbitum-design-system/AGENTS.md` — the design rules every component and style must follow.

## Overview

- **Astro 7** static site on **Nimbus** (`@cloudflare/nimbus-docs`), the framework behind developers.cloudflare.com. Pages are **MDX**.
- **Node.js 24**, **npm**. Dev server on port **1111** (as cloudflare-docs).
- Default branch: `main`.

## Commands

```sh
npm run dev           # dev server, http://localhost:1111
npm run build         # static build to dist/ — validates MDX, frontmatter schemas and internal links
npm run check         # astro check (types + content schemas)
npm run lint:docs     # nimbus-docs lint; needs a prior build (reads .nimbus/)
docker compose up --build       # production image (nginx) on http://localhost:8080
docker compose up --build dev   # dev container with live reload on :1111
```

There are no unit tests. A content change is validated by `npm run build` and `npm run lint:docs`.

## Layout

```
src/
├── content/
│   ├── docs/          # one MDX per page; path = URL. Every folder has index.mdx
│   ├── partials/      # reusable MDX, included with <Render file="orbitum/cli-install" />
│   ├── changelog/     # one entry per file: <product>/<YYYY-MM-DD>-<slug>.mdx
│   └── directory/     # one YAML per product (Directory page, changelog product names)
├── api/openapi.yaml   # source of the generated API reference at /api
├── components.ts      # MDX globals — components usable in MDX without import
├── components/
│   ├── orbitum/       # Orbitum MDX components (HomeHero, LinkCard, Pill, ChangelogEntries…)
│   ├── ui/            # Nimbus registry components (installed with `npx nimbus-docs add`)
│   ├── Header.astro, Footer.astro, TocFooter.astro, OrbIcon.astro, Logo.astro
├── layouts/           # BaseLayout (fonts, tokens, theme script), DocsLayout (3-column shell)
├── styles/
│   ├── globals.css, prose.css     # Nimbus base styles (--nb-* variables)
│   └── orbitum/                   # tokens.css, fonts, icons.json copied from the design system; theme.css
├── site.ts            # header nav, dashboard URL, footer links
└── content.config.ts  # collection schemas (frontmatter fields)
astro.config.ts        # Nimbus config: site, sidebar (explicit, after the mockup), API reference, lint rules
assets/                # the developer-site mockups (reference only, not served)
```

## How the theme works

Nimbus components read `--nb-*` variables. `src/styles/orbitum/theme.css` maps each one to an Orbitum token from `tokens.css` (e.g. `--nb-primary: var(--text)`). The theme toggle sets both `data-mode` (Nimbus) and `data-theme` (Orbitum) on `<html>` in `BaseLayout.astro`, so both token sets switch together.

- Never write a literal colour, font, radius or shadow. Use a token. If one is missing, add it to the design system first, then copy `tokens.css` again.
- `tokens.css`, `fonts/` and `icons.json` are copies from `../orbitum-design-system`. Update them by copying, not by editing here.
- Visual reference: `assets/pages/*.html` and `assets/previews/*.png`.

## Sidebar

The sidebar is explicit in `astro.config.ts` (`sidebar.items`), matching the mockup's groups. A top-level group without a landing page renders as an uppercase section label (custom logic in `src/components/ui/sidebar/Sidebar.astro`). A new page does **not** appear in the sidebar until you add a `link(...)` for it, unless it lives in an autogenerated folder (`style-guide/`).

## Frontmatter

Schema: `src/content.config.ts`. Required: `title`. Expected: `description`, `pcx_content_type` (Cloudflare's taxonomy: `overview`, `get-started`, `concept`, `how-to`, `tutorial`, `reference`, `troubleshooting`, `navigation`, `changelog`, …). Optional: `products`, `reviewed` (also used as the "Updated" date), `difficulty`, `tags`, `template: splash` (no page header, wide column), plus the Nimbus fields (`sidebar`, `tableOfContents`, `draft`, `noindex`, `banner`, `prev`/`next`).

## Content rules

From the Orbitum content style (`../orbitum-design-system/docs/05-content-style.md`):
- Sentence case everywhere. No full stop on headings or labels. Units on every number. 24-hour time.
- Sample data only: `acme-demo`, `example.com`, `203.0.113.0/24`, `198.51.100.0/24`. Never real customer names.
- Status uses the standard words (Healthy, Needs review, Critical, Running, Simulated) and `<Pill>`; Simulation lab content carries `<Simulated />`.

## Common mistakes

1. Unescaped `{`, `}`, `<`, `>` in MDX prose — wrap them in backticks.
2. Using a component that isn't registered in `src/components.ts`.
3. Full URLs or relative links for internal pages — use `/connect/azure/`.
4. Skipping heading levels.
5. `$` before shell commands, capitalised code-fence languages (`json`, not `JSON`; `txt` for output).
6. YAML strings containing `: ` (e.g. in `openapi.yaml` descriptions) — quote them.
7. Adding a component to `src/components.ts` without adding it to `/style-guide/components/`.
8. Hand-copying a Nimbus registry component — use `npx nimbus-docs add <slug>`.
